# Российские банковские интеграции

В наборе есть один исполняемый офлайн-профиль и два разобранных контрпримера.
Это примеры исходящих выплат и платёжных поручений. Приём оплаты по ссылке
не подменяет выплату клиенту.

| Банк и продукт | Что сохранено | Что проверяем |
| --- | --- | --- |
| Райффайзенбанк, одностадийная выплата через СБП | Полная официальная OpenAPI 3.0.3, профиль, независимые синтетические запросы и ответы | Генерация Ruby-адаптера, точная сумма в рублях, заголовки, создание, опрос, отказ и безопасное поведение при повторе |
| Т-Банк, массовые выплаты A2C/E2C 1.46 | Полная официальная OpenAPI 3.0.2, разбор и намеренно неподписанные примеры | Распознавание ограничений: сертификатная подпись, Init → Payment, POST для проверки статуса |
| Точка, исходящее платёжное поручение | Разбор статусов и выбора операции по официальной документации | Подпись человеком, ожидание исполнения, отличие исходящего поручения от эквайринга |

Источники Райффайзенбанка и Т-Банка извлечены из JSON-объекта
`__redoc_state.spec.data` официальных страниц. Все пути, схемы и примеры
сохранены. В `provenance.json` указаны адрес страницы, дата получения, SHA-256
исходной страницы и извлечённой спецификации. Это полные исходные контракты;
файлы `integration.yml`, `review.yml` и `fixtures.json` написаны для Paygen.

## Райффайзенбанк: исполняемый пример

Профиль выбирает `POST /v2/payouts` и `GET /payout/v2/payouts/{id}`.
Входная сумма `"1110.01"` превращается в JSON-число `1110.01` рублей с точной
десятичной сериализацией. `payoutParams.bankId` содержит идентификатор участника
СБП, полученный из списка банков. Это отдельное поле, отличное от БИК.
Авторизация использует `Authorization: Bearer secretKey`.
[Официальный контракт](https://pay.raif.ru/doc/payout.html)

Профиль ограничен выплатой физлицу без фискализации: `fiscal=false`.
Счёт списания, назначение платежа, телефон и `bankId` поступают от приложения.
Тестовые реквизиты синтетические. `COMPLETED` соответствует `approved`,
`DECLINED` — `rejected`. `WAITING_CONFIRMATION`, `DRAFT`, `ON_SIGNING` и другие
состояния ожидания остаются `in_progress`.

```bash
bundle exec bin/paygen init fixtures/raiffeisen_payouts/upstream/openapi.json \
  --output /tmp/paygen-raiffeisen-demo
bundle exec bin/paygen generate /tmp/paygen-raiffeisen-demo
bundle exec rspec spec/russian_banks_spec.rb
```

Первые две команды только создают локальные файлы. Тесты вызывают
сгенерированный адаптер с подставным транспортом и проверяют точный HTTP-запрос;
они не обращаются к банку. Исходная спецификация остаётся неизменной.

У банка описан уникальный `id`, но подтверждённую гарантию повторной отправки
с произвольным `Idempotency-Key` из этого вывести нельзя. Поэтому выбран
режим `reconcile_before_retry`: Paygen не добавляет выдуманный заголовок;
после подтверждённого создания повтор возвращает сохранённый результат,
а после неоднозначного ответа требует сверки по исходному `id`.
Сбой или HTTP 404 при сверке не разрешает повторную выплату. Для нескольких
процессов и перезапуска приложения необходимо подключить общее долговечное
хранилище состояния.

Webhook сознательно не входит в этот профиль: документированный HMAC
использует строку `amount|id|statusValue|statusDate`, поэтому общий режим
HMAC по исходным байтам JSON здесь не подходит. Двухстадийные заявки,
пакеты выплат и фискализация также требуют отдельных сценариев.

В исходных примерах встречаются числовые `inn`, `currencyOperationCode` и
`agreementNumber`, хотя соответствующие схемы требуют строки. Снимок
сохраняет эти противоречия. Наш проверяемый пример не использует эти
необязательные поля. Это полезная проверка качества источника: пример
запроса нельзя автоматически считать достовернее его схемы.

## Т-Банк: подпись и подтверждение выплаты

У `Init` в исходной спецификации стоит `security: []`, но тело требует
`DigestValue`, `SignatureValue` и `X509SerialNumber`. Значит, отсутствие
`securitySchemes` не даёт оснований отправлять запрос без подписи.
В актуальной документации выплат описаны RSA и ГОСТ; подпись `Token`
для отдельных методов привязки карт и справок не заменяет подпись выплаты.
[Официальная документация 1.46](https://www.tbank.ru/business/online-payments/dev/payouts/)

`Init` возвращает идентификатор и состояние `CHECKED`; затем нужен `Payment`.
`Success=true` подтверждает результат запроса, а не завершение всего сценария.
`GetState` вызывается методом POST и тоже имеет подписываемое тело.
`Amount=1751` означает 17,51 рубля. Отмена карточной выплаты этим продуктом
не предусмотрена.

```bash
bundle exec bin/paygen inspect fixtures/tbank_payouts/upstream/openapi.json --format json
```

`review.yml` перечисляет незакрытые требования. Это материал для подготовки
интеграции; готового адаптера Т-Банка набор не обещает. Тест доказывает, что
неподписанный пример нарушает схему, а стандартная генерация без необходимых
семантических решений останавливается.

## Точка: создание не равно исполнению

У исходящего поручения `WaitingForCreate` означает ожидание подписи в
интернет-банке. `Created` также не является финальным подтверждением выплаты;
`Paid` обозначает исполнение. Для такого сценария нужен шаг подписи и
последующая сверка.
[Платёжные поручения](https://developers.tochka.com/docs/tochka-api/opisanie-metodov/platezhi)

Название `Create Payment Operation` относится к созданию эквайринговой
платёжной ссылки. Выбирать его как исходящую выплату только по слову
`Payment` нельзя.
[Платёжные ссылки](https://developers.tochka.com/docs/tochka-api/opisanie-metodov/platyozhnye-ssylki/bez-fiskalizacii)

При подготовке примера 5 сентября 2026 года хосты полной документации и
спецификации Точки отвечали HTTP 502 в рабочей среде. Использована доступная
индексированная официальная документация; полного снимка OpenAPI в наборе нет.
Статус этого примера — `source_unavailable`, он не засчитывается как успешно
импортированный или исполняемый банковский адаптер.

## Что доказывает набор

Зелёный тест Райффайзенбанка доказывает соответствие выбранного Ruby-сценария
закреплённому контракту и независимым офлайн-примерам. Он не доказывает
доступность подключения к продукту, принятие боевых реквизитов, правильность
всех вариантов API или фактическое зачисление денег. Для этого нужен отдельный
банковский приёмочный прогон. Контрпримеры показывают, какие решения требуют
явного уточнения до генерации и отправки запросов.
